# Language Servers and Language-Tooling Architecture: The State of the Writing, Late 2026

*A literature survey, written 2026-11-04. Citations in square brackets are keys into [bibliography.md](language-service-bibliography.md), which records each source's date, URL, and how much of it I actually read. Where I could not read or verify something, I say so in the text.*

## Summary of the argument

Ten years after the Language Server Protocol (LSP) was announced, the writing on language tooling has settled into a fairly stable picture, and it is more sceptical than the protocol's own marketing.

1. **LSP won a coordination game, not a modelling game.** The best-argued account is that LSP succeeded because it fixed a two-sided market failure, and because it standardised *presentation* (what a completion widget shows) rather than language semantics [M1, M2]. The M x N story that Microsoft's own documentation still tells [V2] is, in this account, mostly wrong about why it worked.
2. **The hard part is behind the protocol.** A server is a compiler that must accept broken input, track change over time, and minimise latency rather than maximise throughput [M1]. The newest and most detailed practitioner account (2026) lists the concrete consequences: when to answer `initialize`, virtual file systems, cancellation, workspace discovery, layered indexing, and guessing user intent from half-written code [G1].
3. **There are four architecture families, and each is a bet on a language's structure.** Query-based (rust-analyzer and salsa), compiler-as-a-service (Roslyn, TypeScript, clangd, gopls, Pyright, Sorbet), IDE-platform (JetBrains PSI and stubs), and grammar-first generation (Xtext and Langium, Spoofax, Rascal, Lezer and tree-sitter, stack graphs). The best-known author on the first family now argues that query machinery should be the last resort and that *language design* decides what incrementality is achievable [R1, M3].
4. **Grammar-first systems derive structure well and semantics poorly.** Everything in this family derives a parser, a tree, outline, folding, highlighting skeletons, and syntactic completion from a grammar. None of them derives name resolution, types, or semantic completion; each makes the author write scope rules, symbol tables, or constraints, in a declared form (Xtext and Langium scope providers, Spoofax NaBL2 and Statix, tree-sitter `locals.scm`, stack-graph rules) [E1, E5, E9, E10, E13, E11, E15].
5. **Declarative name binding at scale has had a mixed history.** Scope graphs are the strongest theory [E9, E10] and stack graphs the strongest production deployment [E11], yet GitHub's repository for the latter now says it is no longer supported [E12]. The most direct analogue to "derive a server from a parser plus small hooks" reported under 1,000 lines per language, accepted low precision, and covered only dynamic languages [E17].
6. **Evidence in this area is usually weak.** Typical claims are line-count reductions, vendor benchmarks, or small hand-written test sets, judged without an independent oracle [E17, E18, P1, E4, C4]. The few strong practices are structural: snapshot tests with cursor markers [R7], from-scratch-versus-incremental comparison and fallback-reason metrics [C6], and crash fuzzing [T1].

The rest of this survey fills in that picture. It ends with the questions the literature says a proposal to derive a language service from a grammar must answer (section 8).

## 1. Why the protocol exists, and how it has evolved

### 1.1 The standard story and the better one

The standard explanation is arithmetic. With M editors and N languages, pre-LSP tooling needed M x N plugins; with a common protocol it needs M + N. Microsoft's current extension documentation still tells exactly this story, adding that a server in its own process protects the editor from heavy analysis [V2]. The 2019 DSL case study in my reading list tells it too [E19], as does a 2025 paper about generating servers for language families [E18].

Matklad's 2022 essay is the sharpest dissent [M1]. His argument has four parts, which I find persuasive and which I summarise because the design leans on them:

- The glue between a server and an editor is tiny compared to either side. He cites the VS Code plugin for rust-analyzer at about 3.2k lines, Neovim at 2.3k, and Emacs at 1.2k [M1]. I could not independently count these; they are his figures.
- Before LSP the problem was not that M x N was too large but that N was nearly zero and M nearly one. Language servers were hard to build, and most editors lacked high-level extension points such as a first-class completion provider. He contrasts VS Code's `CompletionItemProvider` with Emacs and Vim, which expose low-level cursor APIs on which competing frameworks are layered [M1].
- LSP therefore solved a two-sided market problem, and Microsoft, being a vendor of both languages and editors, was positioned to solve it [M1].
- The M x N framing predicts one LSP client per editor, yet Emacs has two and one server's manual lists six Vim clients; and Microsoft's own editor ships a separate LSP library inside every language extension, so even VS Code does not exploit M + N [M1].

Discussion on the post shows the disagreement has not been settled. One commenter calls it a strawman: the left-hand picture in the standard diagram was never meant to be built, which is why a shared protocol was needed [D2]. I treat that as a fair point about rhetoric and not a refutation of the empirical claim about glue size. I also note that this is discussion, not authority.

The same author's later critique [M2] adds a technical dimension, and I think it is the most useful single document for anyone designing a layer *above* LSP. Its central point is that LSP is "focused squarely on the presentation": requests map to editor widgets, not to semantic entities. The outline, breadcrumbs, selection ranges, and folding are all views of one syntax tree, yet LSP has no "get the tree" request and offers separate requests for each widget so each can be tuned [M2]. That is why one language's rich model can serve the same completion box as another's. It is also why the protocol is awkward for anything that wants structure: the missing "function body" kind for folding ranges is a small, concrete example [M8], and rust-analyzer's list of non-standard requests is a large one [R8].

### 1.2 History and versions

LSP was announced in June 2016, and TypeFox says its Xtext got LSP support a few months later [E17, E2]. The specification history is recorded in the change log of the current specification page [L2]. In outline:

- **3.0 to 3.15 (to early 2020):** the original feature set. Notable later additions include `prepareRename` (3.12), file operations in workspace edits (3.13), location links (3.14), and progress reporting, selection ranges, and server/client info (3.15) [L2].
- **3.16 (2020-12):** semantic tokens, call hierarchy, monikers, linked editing, code action resolve, and change annotations [L2].
- **3.17 (2022):** the large release. It added inlay hints, inline values, type hierarchy, notebook documents, the pull diagnostic model, position encoding negotiation, completion label details, and guidance on stale requests; it also introduced a machine-readable **meta model** [L1, L2]. Matklad had complained that until then the source of truth for the spec was an informal markdown document from which every implementation extracted its own types [M1]. Gopls, for example, now generates its protocol types mechanically from the Microsoft schema [C3].
- **3.18 (2026):** the changelog dates it 06/04/2026. Every other date in that changelog is month-first (for instance 3.16 is 12/14/2020), so I read this as 4 June 2026, but the page does not state the format [L2]. It adds inline completions, dynamic text document content, a refresh request for folding ranges, multi-range formatting, snippets in text and workspace edits, code action kind documentation, and an `applyKind` for combining completion defaults [L2]. I read the specification text and the change log, and I only skimmed the 3.18 additions in detail.

Three mechanisms in the specification matter more than any single feature, and every design that sits on top of LSP inherits them.

**Capability negotiation.** Features are kept compatible through capability flags exchanged at initialisation, and clients are told to ignore server capabilities they do not understand [L2]. Servers must therefore be written to degrade by client. JetBrains' documentation shows how uneven the client side can be: its LSP client added semantic tokens in 2024.2, pull diagnostics in 2025.1, inlay hints and folding in 2025.2, document symbols, breadcrumbs, and hierarchies in 2025.3, and rename and code lens only in 2026.1 [J1]. A server author cannot assume parity even among mature clients.

**Document ownership and synchronisation.** `didOpen`, `didChange`, and `didClose` are mandatory as a group; once a document is open the client owns its content and the server must not read the file from disk [L2]. Both full and incremental sync exist. The specification stresses that open and close are *ownership* events, not statements about what the user sees, which is the stated reason that pull diagnostics were introduced: a server inferring UI state from those events can produce false positives, and a push-only model cannot prioritise the file being typed in [L2].

**Ordering and staleness.** Responses may be reordered when correctness is unaffected, but the spec says a server should not reorder a definition request past a rename [L2]. Its implementation notes recommend that *clients* cancel or ignore stale results, and that servers should *not* cancel merely because a state change is queued, since the client may still use the result; a server that detects invalidation may fail the request with `ContentModified` [L2]. Rust-analyzer instead cancels in-flight work when an edit arrives and applies the edit in place [M6]. These two positions are in tension, and I return to it in section 4.

### 1.3 Position encodings, semantic tokens, pull diagnostics

**Position encoding.** Before 3.17 every column was a count of UTF-16 code units. Since 3.17 client and server can negotiate UTF-8, UTF-16, or UTF-32, with UTF-16 the mandatory default; the server chooses from the client's ordered list and the spec says conversion is best done server-side, where the line is available [L1, L2]. Matklad's complaint predates negotiation: UTF-16 is the wrong number to show a user as a column and not useful to a server, and his preference is UTF-8 code units, with code points the "most agreeable" alternative [M2]. Practitioners working today still keep offsets and UTF-8 internally and convert at the boundary using a per-file line index [G1]; gopls' protocol layer includes a mapper between UTF-8, UTF-16, and token positions [C3].

**Semantic tokens.** Introduced in 3.16, they let a server mark tokens with a type and modifiers, integer-encoded with optional deltas, over a legend negotiated at start-up; clients declare whether multiline and overlapping tokens are supported [L2]. VS Code frames semantic highlighting as an addition to TextMate grammars, which tokenise a single file with regular expressions, and lets language extensions register providers directly or through a server [V3]. The protocol design makes sense for presentation, but I note from the same specification that the request is per-file and large; it is not the right shape for state that changes under the client's feet, which was matklad's "level-triggered versus edge-triggered" complaint [M2].

**Pull diagnostics.** Push diagnostics are "owned" by the server and replace rather than merge, and in project-system languages are not cleared on close [L2]. Pull diagnostics (3.17) let the client choose what to compute and when, and a refresh request lets the server say results changed [L2]. For a server author, the practical meaning is that the client can now ask for the open file first, which fixes the prioritisation problem described above.

**What remains awkward or missing.** I found five recurring complaints in recent sources, and I flag which are from primary maintainers.

1. *Interactive, multi-step refactorings.* The Go team's own 2025 to 2026 proposal says LSP refactoring is limited to operations needing no user input, that a server-to-client request for answers is not scalable because of blocking and timeouts, and that previews are meaningless when edits depend on answers [T2]. This confirms the 2023 complaint [M2].
2. *State synchronisation.* Highlighting, outline, and diagnostics are derived data, but LSP treats most as requests, so clients re-query conservatively or show stale results; the Dart protocol's subscription model is the cited counter-example [M2]. Glancer's author hits the same wall: document symbols cannot be refreshed, so if they are not ready they stay stale until the client asks again [G1]. 3.18 adds a folding-range refresh [L2], which shows the gap is being closed one feature at a time.
3. *Causality.* Notifications carry no reply, so a client cannot know whether a server edit reflects its latest `didChange`; document versions help but miss cross-file changes [M2].
4. *Configuration.* LSP has several mechanisms but none is blessed, so a server and an editor may share no common way to configure it [D1, a commenter's experience].
5. *Protocol extension is a social process.* The folding-kind example shows that adding a kind is technically trivial but hard if you are not VS Code [M8]. Rust-analyzer's long extensions list is the practical consequence [R8]. Its own architecture document puts the policy plainly: the `ide` API is unstable while the LSP interface is stable, and the project leans on external stability guarantees where it can [R6].

### 1.4 Notebooks and agents

LSP 3.17 added notebook document synchronisation [L1]. I did not read that section closely and I found no independent evaluation of how well servers support it. Separately, by 2026 coding agents have become a visible consumer of language servers; I take that up in section 7.

## 2. What makes language servers hard in practice

The anchor for this section is a September 2026 article by the author of Rust Glancer, an experimental low-memory Rust server [G1]. It is a single-author blog post, written by someone who disclaims expert status and says he reads rust-analyzer code without being a maintainer. I weight it as a well-organised catalogue of encountered problems, corroborated where I can by the sources it cites, not as a survey. Its thesis, repeated in different forms, is that building a server "means having to produce useful answers from partial information" [G1]; a compiler has a binary notion of done, a server does not.

### 2.1 The catalogue

I read the article in full and group its content as follows.

**Start-up is a design problem.** The first message, `initialize`, blocks the client until answered, yet at that moment the server knows nothing about the project and indexing is "a lot of work". The article's answer is to do the least work that makes queries possible: validate configuration and reply. Rust-analyzer then schedules discovery after the reply; Rust Glancer stays passive until the first query [G1]. The first queries are typically `didOpen`, `inlayHint`, and `documentSymbol`, possibly with a `didChange` racing in between [G1]. The specification's own rule that servers must not read an open document from disk [L2] sits awkwardly with the reality that most analysis needs the disk too.

**LSP has no file system, but servers need one.** The protocol speaks of documents and edits, yet analysis of one file in isolation "stops being useful fairly quickly" for most languages. The consequence is a virtual file system and *source generations* (identifiers for the state of the sources a request runs against), used to keep internal state consistent and to cancel invalidated work [G1]. Rust-analyzer's architecture document states the same invariants from the inside: the analyser never does I/O, files are opaque ids, and the VFS provides consistent snapshots [R6]. One commenter on the discussion thread took the other side, calling "LSP assumes it's the source of truth" evidence of bad protocol design [D3], which is a critique of the same fact.

**Queries have very different costs and must run in parallel.** Hover is cheap, find-references is not. The server needs a loop that separates mutating from non-mutating work, lets reads run in parallel, cancels reads when state changes, and, if it uses async, serialises incoming messages so `didOpen` and `didChange` cannot be reordered [G1]. This is the same design question matklad poses as strong versus relaxed consistency [M6].

**Not everything can be refreshed.** `workspace/inlayHint/refresh` lets a server say "try again", but document symbols have no such refresh, so a server that is not ready must either block or accept staleness [G1].

**The layers of indexing are the real architecture.** The article's list for Rust is parsing, an *item tree* (per-file summary of declarations), a *definition map* (what is visible where, resolved with fixed-point loops because imports and macro expansion depend on each other), an item index (linking impls to types and traits), body resolution, and then type inference and trait solving [G1]. Different requests need different depths: document symbols need only a parse, hover on a signature needs the definition map, inlay hints need type inference, and find-references needs a plan to avoid walking every body [G1]. "The end shape" of indexing, the author says, is dictated by the queries you want to answer [G1]. This is also the shape of the rust-analyzer crate layout [R6].

**Workspaces are underdetermined.** An opened folder can contain several projects, be a crate inside one, or contain stray files. Eager discovery wastes CPU; lazy discovery looks broken. Rust-analyzer runs all workspaces in one process, so one failure puts the whole server in an error state; Rust Glancer routes each workspace to its own process, at the cost of fighting the protocol [G1]. The author concludes there is no right answer, only decisions that users will disagree about [G1].

**The protocol leaks into the core.** Line and UTF-16 columns force a line index per file; edits need the file's line-ending convention; parsing needs project metadata (the Rust edition decides whether `gen` is a keyword), so even parsing is stateful [G1].

**Incorrect code is the normal case.** Parsing must always succeed; duplicate methods, impls of missing traits, and half-typed declarations are routine. Completion is about the surroundings of the cursor, not what is under it: after a dot, after `::`, inside a struct literal, in an empty file [G1]. The article describes a ton of special cases and calls the whole exercise guessing the user's intent.

### 2.2 What the discussion adds

The thread on the article is useful for a different reason than the post. One commenter says almost all of it applies to any language and that the basics (async handling, UTF-16 conversion) are not that hard; the hardest thing in his own server was useful completion in a syntactically broken document [D3]. Another points out a language-design effect: if a language forces qualified names, a server can still rename reliably while parts of the project fail to parse, but with glob imports "you are in trouble" because a name could come from anywhere [D3]. A third separates two jobs a server does, best-effort *editing help* on incomplete code and *reliable, exhaustive analysis* of code that compiles, noting that they pull in different directions [D3]. I consider that last distinction under-appreciated in the formal literature, and I use it in the rubric. These are comments on a discussion site, whose scores and counts I could not independently verify beyond the numbers the search API returned.

### 2.3 The ideas the article builds on

The article's references are a compact reading list, and I read the cited posts: the three-architectures post [R1], the durable-incrementality post [R2], the heart-of-a-language-server post [R3], and matklad's resilient-parsing material [M4] in full or nearly so, and the find-usages post [R4] only in part. Their common claim is that a language server is not a compiler with a socket: it must analyse code that is wrong, over a stream of edits, optimising latency, and "turn the architecture on its head to have an acceptable latency at all" [M1]. Matklad adds the historical observation that language servers are the counter-example to "never rewrite": IntelliJ and Eclipse wrote their own Java compilers, Roslyn rewrote C#'s, Dart ended up with three implementations, and rust-analyzer "decisively won" over the attempt to evolve rustc into RLS [M1]. The two exceptions he knows, C++ and OCaml, reuse batch compilers because their languages require forward declarations and header files [M1, R1].

## 3. The architecture families

### 3.1 Query-based, incremental, demand-driven: rust-analyzer and salsa

Rust-analyzer is the reference implementation of the third architecture in matklad's taxonomy [R1]. Its design, from its own architecture document [R6] and the blog posts [R1, R2, R3], has these features:

- **Inputs are explicit and derived data is lazy.** Source texts and a crate graph are the only ground state; everything else, including name resolution and types, is derived on demand [R6].
- **Salsa records dependencies and cuts off early.** Every function call inside the analysis is instrumented; after an edit, results are revalidated lazily against a global version number. If a recomputed result equals the old one, invalidation stops there (*early cutoff*) [R2, R1]. "Durability" adds a version vector so that edits to user code skip revalidating the standard library [R2]. The theory sits in the build-systems literature: *Build Systems a la Carte* separates scheduler from rebuilder and defines minimality and early cutoff [C8], and matklad cites it as the canonical paper [M3]. I read only the introduction and definitions of that paper.
- **The work is in the shields.** Matklad's recurring lesson is that the effort of building on an incremental engine goes into designing *early-cutoff shields*: for example, an item tree that is stable under edits to function bodies, and a syntax tree without positions so whitespace edits do not leak [R2, R6]. The stated invariant is that typing inside a function body never invalidates global derived data [R6].
- **The syntax tree is a value.** It carries no semantic information and is built per file so files parse in parallel; the parser never fails and returns a tree plus errors; tree nodes may be missing even when the grammar forbids it [R6].
- **The IDE API is not LSP.** The `ide` crate exposes plain data in editor terms (offsets, labels), deliberately designed for an imagined perfect client, and only one crate knows LSP and JSON [R6]. This is the practical form of the advice to treat LSP "as a serialization format, not as an internal data model" [M1].
- **Syntax to semantics via the parent chain.** For any cursor-based request the server must map a syntax node to a semantic element. The method that survives scrutiny is recursive: find the semantic parent, ask it for children, and match on source syntax. It works because syntactic nesting equals semantic nesting, and it costs laziness at the file level (a Rust file's place in the module tree is not known from the file alone) [R3]. Roslyn and Kotlin do the same thing, per the same post [R3]. The span-based alternative, which attaches spans to semantic objects, is too slow because it requires analysing the whole unit, and loses the syntax identity that refactorings need [R3]. Glancer's author, having full analysis resident, chose the span approach and implements refactors as separate algorithms [G1], which shows the choice is architecture-dependent.

Salsa's own book has a tutorial for a small language ("calc") with sections on a parser, error reporting, and a checker, and reference material on durability, the algorithm, and cycle handling; I could only extract the table of contents, so I do not characterise it [C7].

**The sceptical turn.** In February 2026 matklad published "Against Query Based Compilers" [M3]. The argument: a query-based compiler is the plain application of incremental computation, and its limit is a property of the language, not the engine. Update work cannot be smaller than the change in the result, as the hash-function example makes plain, and even a potential avalanche costs time and memory to rule out. His advice is to design the language so that coarse, independent chunks exist, and to push queries as far down the pipeline as possible. The Zig sketch: parse and name-resolve each file independently in parallel because every name is declared explicitly; extract a per-file summary; evaluate signatures sequentially in one phase that re-runs when a summary changes; check function bodies in parallel; changing a body cannot create errors elsewhere [M3]. Rust cannot do this because macros need crate-wide name resolution and trait impl lookup depends on every file [M3]. He also notes that per-file diffs applied to a global map can beat a recursive query structure [M3]. In his reaction to Rust Glancer he adds that the rowan tree library is the wrong default for the 99% of dependency code that is only shallowly analysed [G2].

My assessment: these are opinions of the person best placed to have them, but they are also an argument *for* designing around laziness and per-file independence, and the evidence offered is architectural reasoning plus experience, not measurement. Glancer's author reports a competing design (eager index persisted to disk, lower RAM) but I found no published head-to-head benchmark of the two on the same hardware; a search-engine summary of the Show HN discussion says the author's benchmarks came from one 8 GB laptop, which I could not verify from a primary source [G3 was fetched but not read].

### 3.2 Compiler-as-a-service

**Roslyn and the red-green tree.** Roslyn exposes the compiler's own data structures through a public API [C1 describes the tree; the "compiler as a service" framing is from background knowledge and search snippets and I did not verify it against a primary Roslyn document]. Lippert's account of the syntax tree is primary: nodes are immutable and persistent, so edits reuse most of the old tree; but immutability conflicts with parent pointers and absolute positions, so a *green* tree stores only widths and children, and a *red* facade, built lazily per edit, supplies parents and positions [C1]. This is the ancestor of rowan-style trees and is the same pattern as "syntax tree is a value type" in rust-analyzer [R6].

**clangd.** C and C++ can be parsed one translation unit at a time, so clangd runs the real clang parser in a loop per open file, keeps the AST for cursor queries, and takes its configuration from compile commands [C2]. Because an AST for one file lacks what lives in other files, it adds an index of symbols, references, and relations with stable symbol ids, layered as a dynamic index for open files and preambles, a persisted background index, and optionally a prebuilt or remote index [C2]. The later fuzzing paper notes that clangd alone has over 500 crash issues, a reminder that reusing a compiler's parser does not make a server robust [T1].

**gopls.** The implementation overview describes a cache layer as the largest and most complex part: sessions, folders, views, immutable snapshots after each edit, overlays for unsaved text, memoized computations, and a persistent file cache for xrefs, method sets, and type references that delivered fast restart and lower memory in a v0.12 redesign [C3]. Notably, its parsing package performs "tree repair to work around error-recovery shortcomings of the Go parser", an admission that a batch-oriented parser's error recovery is not enough for a server [C3].

**TypeScript.** Hejlsberg's March 2025 announcement of a Go port reports roughly 10x faster command-line checking on six public repositories (for instance 77.8 seconds to 7.5 seconds on VS Code's 1.5 million lines) and editor project load dropping from 9.6 to 1.2 seconds, memory about halved, and a move to LSP [C4]. These are vendor measurements on an unfinished port and the post calls them representative. Search snippets report TypeScript 7 reaching release in mid-2026 with an LSP server and without a stable programmatic API at first, which would strand embedders; I could not fetch the primary announcement (403) and treat this as unverified [see the could-not-fetch list]. The architectural lesson I take from the primary source is only that the largest TypeScript-using ecosystem chose to rewrite a mature compiler for editor latency and to adopt the standard protocol.

**Pyright.** Its documentation describes a lazy, just-in-time type evaluator able to evaluate the type of any identifier without a top-to-bottom pass, in contrast to mypy's repeated passes until convergence, and claims 3x to 5x speed [C5]. The claim is the maintainers' own.

**Sorbet.** Zimmerman's account of making Sorbet incremental is the best published *measurement-driven* story I found [C6]. Sorbet is not fully incremental: when an edit changes definitions it falls back to a full check. By logging a reason for every fallback, the team found "changed definition" accounted for half of slow-path edits, cut the full-check fraction from 19% to 10% of edits, and quadrupled incremental-mode tests to 8% of the suite. He quotes a colleague that Sorbet got away with simple incrementality for years because base-case speed was good enough, until codebase growth ended that [C6]. Matklad lists Sorbet, with IntelliJ, as an instance of the map-reduce architecture [R1].

Across this family the pattern is: reuse of the compiler front end is cheap at first and costly later; and error recovery, project configuration, and cross-file indexes have to be added to get a server out of it.

### 3.3 IDE-platform approaches

**JetBrains.** The platform's model is a *PSI* tree over a concrete syntax tree, with file-based indexes and *stub indexes*. A stub tree is a compact serialized subset of PSI containing the declarations visible from other files; PSI can be backed by AST or by stubs and the switch is transparent, but touching a node that is not in the stub forces a parse [J4]. While indexing runs the IDE is in "dumb mode" and features needing indexes are disabled [J4]. This is the map-reduce architecture in matklad's taxonomy, the "stubs with unresolved types" design [R1]. Language injection treats embedded languages as separate small files bound to context, and can join several string fragments [J4].

Two of JetBrains' recent writings matter for the debate. Its SDK documentation says the LSP integration "shouldn't be considered" a replacement for the Language API, which gives deeper integration [J1]. And its 2025 and 2026 announcements show LSP support as a closed-source, commercial-IDE feature that is being opened up: free for third-party plugins in 2025, with the client API being open-sourced and renamed in the 2026.1.4 to 2026.2 timeframe, in part because a plugin using it silently failed in Android Studio and another author wrote a whole client from scratch [J2, J3]. JetBrains also tells plugin authors using the community client LSP4IJ not to migrate for its own sake [J3]. Search results (not opened) report that JetBrains discontinued its Fleet IDE in December 2025.

**Grammar-Kit** belongs here and in section 3.4. It turns a BNF grammar into a parser and PSI classes and generates a lexer via JFlex, but "resolve and other non-trivial functionality" is mixed into the generated PSI by hand, and the Gradle plugin cannot process those mixins because of a generate-compile cycle [J5]. Many open-source IntelliJ language plugins are built with it [J5].

**VS Code.** The Microsoft documentation presents two routes: register providers (hover, completion) directly in the extension host, or write a language client that talks to a server in another process [V4, V2]. It documents semantic highlighting as layered on TextMate [V3]. Matklad praises `vscode.d.ts` as an architecture: IDE features are first-class extension points that know nothing of LSP, which is just a library the language extensions use [M1].

### 3.4 Grammar-first and specification-driven generation of language services

This is the family closest to the question the survey was commissioned to inform, so I spend the most space here and organise it around one question for each system: *what does the system derive from the grammar or specification, what does it make the author write, how is that authored part expressed, and where does it break down?* The table that follows summarises; the prose gives the evidence and its quality.

| System | Derived from the grammar or specification | Author-written (and how expressed) | Where the sources say it strains |
|---|---|---|---|
| Xtext, Langium [E1, E2, E5] | Parser, AST types, default hierarchical scoping by `name`, cross-reference linking, document symbols, go to definition, find references, completion (syntactic and reference-based), diagnostics for parse and link errors | Scope providers and scope computation (code, via dependency injection); validators per node type; type computation ("no default implementation"); caches | CST memory and parse time at scale; no parallelism in JS; parsing blocks the server [E4] |
| Spoofax (SDF3, NaBL2, Statix) [E9, E10, E7] | Parser (SDF3, GLR); generated Eclipse and IntelliJ editor plugins [E7] | Name binding and typing in scope-graph and constraint languages | Spoofax 3 "under heavy development", no confirmed LSP generation [E7] |
| Rascal [E6] | A server shell that hosts services | Each service is a function: parser, summarizer, outliner, lenses, hover, definitions, references, code actions | "Almost zero cost" is the docs' claim; the services are still written by the author [E6] |
| JetBrains Grammar-Kit [J5] | Parser, PSI classes, element types, lexer skeleton | Resolve and all non-trivial behaviour as hand-written mixins | Generator cannot process mixins in Gradle [J5] |
| Lezer with CodeMirror [E14] | Incremental error-tolerant parser, tree | Highlighting, indentation, and folding as node properties attached to grammar nodes | Trees are compact, "awkward" for refined analysis [E14] |
| tree-sitter [E13] | Incremental error-recovering parser | Queries: highlights, locals (scopes, definitions, references), tags (definitions, references) | Search-based, imprecise navigation; locals are single-file [E13] |

| Marr et al. [E17] | Server logic from a small structural interface | Under 1,000 lines per language that report declarations, references, scopes | Low precision; no error recovery assumed; dynamic languages only [E17] |
| Typelang for Neverlang [E18] | Servers and three LSP plugins | Type-system DSL per language artifact | Own framework; character-count evidence [E18] |

#### Xtext and Langium

Langium's stated purpose is to lower the barrier to creating a DSL by providing a grammar language such that "out-of-the-box functionality is based on the information extracted from a grammar declaration"; it was initiated in 2021 as the TypeScript successor to Xtext, which began in 2008 and added LSP in 2016 [E2]. The first release's service list is a good picture of what a grammar alone gives: completion, validation, go to definition, find references, document highlights, and document symbols, with cross-file linking, testing utilities, and more defaults still on the roadmap [E2].

The workflow documentation draws the line between derived and authored explicitly. Writing the grammar generates the AST types, but "the AST is generated with gaps": cross-references are in the tree but unresolved, and the author must fill the gaps with scoping and linking, then write validations [E1]. The document lifecycle defines the states: parsed, content indexed, scopes computed, linked, references indexed, validated, and changed [E1]. The default scope computation exports every named top-level node into a global index and attaches each local symbol to its container; the default scope provider walks from the reference up through containers with inner symbols shadowing outer ones and falls back to the global scope; cross-references cannot be consulted during scope computation [E1]. Customisation is by overriding services through dependency injection [E1]. For languages with types, the docs say computing them is "an additional pre-processing step" for which "there is no default implementation" [E1]. Caches are an explicit author concern, with document-scoped caches cleared on change and workspace caches cleared on any change [E1]. When a document changes, it is re-parsed and dependent documents (found via the reference index) are unlinked and re-linked [E1]; there is no fine-grained incrementality below the document level in this description.

Xtext's equivalent documentation shows the same split [E5]: the grammar declares cross-references; scoping is "usually provided via the scoping API" (an `IScopeProvider` returning an `IScope` for a context object and reference); global visibility comes from resource descriptions in an index, with a default that exports every element that has a qualified name, which the docs call "a good starting point" [E5]. Linking is lazy by default [E5]. Broken cross-references are checked generically by the framework [E5].

What the maintainers say about limits is unusually candid, though it is vendor self-report. In December 2025 TypeFox wrote that both Xtext and Langium run into performance walls: constructing and keeping the CST takes about 80% of memory in Xtext and about 75% in Langium, the Langium parser spends around 60% of its time building the CST, JavaScript runtimes lack shared-memory parallelism so parsing blocks the server and cannot be aborted, and responses degrade into the 1000+ ms range for files above about 1 MB [E4]. They replaced the CST with token metadata in a PL/I server for the Zowe project, concluded the improvements "cannot simply be bolted on", and announced a new Go-based toolkit for high-performance cases, while saying that only a small portion of languages suffer and that Langium remains the first choice [E4]. I note the benchmarks are not published in that post, which limits how far I rely on the percentages. What I do rely on is that the generated-service model assumes a whole-document parse that is not cancellable, which is a *structural* issue the maintainers themselves identify.

On migration, TypeFox's Xtext2Langium generator converts a grammar between the two grammar languages, with documented gaps (the `until` token, enum rules turned into string unions, Ecore data types mapped), and says nothing about moving scoping or validation code [E3]. The grammar moves; the semantics do not.

A 2019 case study with an Xtext-generated server in two IDEs reports that it enabled multi-editor integration [E19]; it is a SWOT analysis, not a measurement, and I only skimmed it.

#### Spoofax, scope graphs, and Statix

The theory is the strongest in the survey. *A Theory of Name Resolution* describes name resolution as two stages: a language-independent *scope graph* constructed by language-specific rules from the syntax tree, then a language-independent resolution calculus and algorithm, proven sound and complete against the calculus [E9]. From the calculus the paper derives language-independent definitions of alpha-equivalence and of rename refactoring [E9]. That last point matters for anyone proposing to derive *rename* and *references*: in this theory they follow from the same binding structure as resolution. *Scopes as Types* extends the framework to structural records and generic classes by treating scopes as the representation of type structure, and introduces Statix, a meta-language for static semantics based on scope graphs and constraints, evaluated on a lambda calculus with records, System F, and Featherweight Generic Java [E10]. I read only the abstracts and introductions of both; they are research papers evaluated on small calculi.

On the practical side, the Spoofax 3 status page says the system "is still under heavy development", lists the implemented meta-tools as SDF3, a GLR parser, ESV, and NaBL2, and says NaBL2 only works for Spoofax 2 language definitions; it generates Eclipse and IntelliJ plugins, not an LSP server, and my searches found no confirmation of generated LSP servers [E7]. A 2025 comparison paper reports Spoofax as "partially" supporting server generation, but I could not confirm what that means from the text I saw [E18].

#### Rascal

Rascal's LSP library lets a language implementer register a language with a name, extension, and main module, and supply a set of *language services*: parsing, analysis (a summarizer that receives a location and a parse tree), build, outline, lenses, hover, definition, implementation, inlay hints, call hierarchy, code actions, and execution [E6]. The documentation claims that it turns "your language implementation into an interactive IDE at almost zero cost" [E6]. Reading the API, I would say what comes at near-zero cost is the *server shell* (protocol, document management, process isolation): every feature beyond parse errors is a function the author supplies. Each registered language runs in its own isolated runtime, a separate JVM and Rascal instance [E6]. The documentation defines a `Focus` as the list of parse-tree nodes around the cursor, from the smallest to the whole tree, and notes it may be empty on parse errors or ambiguity [E6]. That is the same cursor-to-syntax step that rust-analyzer's heart-of-a-server post describes [R3], supplied by the framework.

#### MPS and projectional editing

JetBrains MPS makes the premise different: the editor edits the AST directly, so parsing and erroneous text are not the problem. I fetched only the user guide's table of contents and cannot assess its language-service story; I list it for completeness [E8].

#### Lezer, tree-sitter, and the editor-first parsers

For editor-first parsers, what is derived is a *tree*, and everything else is metadata the author attaches.

Lezer's guide describes an incremental LR parser with generalised-parsing support. On a syntax error it tries recovery strategies in parallel (skip the token, or skip ahead to a place matching the current token) and keeps the one that looks best a few tokens later, marking error nodes in the tree [E14]. Its trees are deliberately "not very abstract": each node stores a type, a range, and children, which makes them compact and reusable across edits and "somewhat awkward" for refined analysis [E14]. In CodeMirror's language-package tutorial, highlighting, indentation, and folding are declared as node properties added to the generated parser (a style-tag map, an indentation function per node type, a fold function per node type), not derived automatically [E14]. The tutorial also says existing batch parsers are usually unusable in an editor because parsing must be incremental and error-tolerant [E14]. Contextual tokens, indentation-sensitive languages, and external tokenizers are handled with escape hatches into code, including a context tracker whose hash determines incremental reuse [E14]. The claim that matters for any grammar-derivation proposal is that **the grammar yields structure, and editor behaviour needs author-supplied node-level declarations**.

Tree-sitter's own documentation gives the same picture with a query layer. A *highlights* query maps captures to theme names. A *locals* query uses a fixed vocabulary, scope, definition, and reference captures, to track local variables within one file, so a reference to a local can be distinguished from, say, a method [E13]. A *tags* query captures definitions and references with a role and kind plus a name and optional documentation, and the docs describe the result as *search-based* code navigation [E13]; the SCIP announcement likewise distinguishes search-based navigation (ctags or tree-sitter; fast, always available, occasionally wrong) from precise navigation (compiler-accurate, needs configuration) [C10]. Tree-sitter's grammar guide shows the practical cost of authoring a grammar: unresolved conflicts must be fixed by precedence, associativity, or declared conflicts, guided by error messages [E13]. Its error handling (ERROR and MISSING nodes) I know only from secondary sources and do not detail here. Matklad's comparison is useful: Tree-sitter's GLR strategy finds many valid small fragments but may not assemble them into an incomplete larger node, while top-down parsing naturally yields incomplete large nodes; his own advice is "just use Tree-sitter" if you want something quickly [M4].

#### Syntactic completion from the grammar: antlr4-c3 and Chevrotain

The most concrete example of derived *completion* is antlr4-c3, a grammar-agnostic engine that, given a parser and a caret position, walks the parser's transition network and returns the token types and parser-rule kinds that can legally appear there, with no need to have parsed the document [E15]. The README is clear about what it does not do: keywords come free, but to offer variables or class names the author must put those entities into their own grammar rules, tell the engine which rules to return, and supply a symbol table from which the actual candidates come [E15]. Chevrotain's content-assist function, from search-result type declarations only, takes a start rule and the tokens before the cursor and returns the possible syntactic paths [E16, partly unverified], and its recovery follows ANTLR3's single-token insertion and deletion and resynchronisation [E16]. The pattern is consistent: **completion splits cleanly into what can syntactically come next (derivable) and which names or members fit (symbol-table and type work, authored)**.

#### Generated servers: two research systems

Marr, Burchell, and Niephaus (DLS 2022) is the closest published analogue to deriving a server from a parser plus small hooks [E17]. They compare the execution-based GraalVM language server, which needs code to be runnable and ideally well tested, with a parse-based design whose language-agnostic interface collects element identifiers, declarations, references, scopes, and documentation from existing parsers (custom parsers and ANTLR) [E17]. The result: under 1,000 lines per language (SOM 920) against a median of 12,055 lines among 20 open-source language servers surveyed (mean 18,985; range 1,577 to 95,878) [E17]. Their own caveats are specific: they assume the parser aborts at the first error and has no incrementality, so they reparse on every change and keep a last-good structure; go to definition returns candidates by element-id equality so precision is low; completion offers variables that have not been defined yet; keeping everything in memory is impractical for millions of lines; parsers took at most 215 ms for 10,000 lines; and they restrict themselves to dynamic languages and leave typed languages as future work [E17]. The evaluation is on three research languages (SOM, Newspeak, SimpleLanguage), precision is argued qualitatively in a table, and there is no independent oracle. Lines of code in the comparison include the protocol implementation in some repositories, which they acknowledge [E17]. This is a candid paper, and its candour is precisely what a reviewer should look for in a successor.

Bruzzone, Cazzola, and Favalli (JSS 2025) go further for language *families* [E18]: a type-system DSL per language artifact, generated servers, and generated LSP plugins for three editors, with a reported 93.48% reduction in characters to implement the type system and 100% automation of plugin generation [E18]. The comparison baseline is the authors' own framework, the metric is characters, and I found no feature-level correctness evaluation in the portions I read. It also states that Xtext is the only tool that automatically generates language servers while being monolithic [E18], which conflicts with Rascal's claim of an LSP generator [E6]; I do not adjudicate.

#### Index formats and code navigation

A separate lineage drops the live server and precomputes navigation data. LSIF let servers run in batch mode to emit resolutions; stack-graphs' authors note that no extant server supported its incremental mode, so each commit meant re-analysing the project [E11]. Sourcegraph then replaced LSIF with SCIP: LSIF's lack of a schema slowed development, opaque numeric ids made debugging hard and incremental indexing complex, and SCIP uses protobuf and human-readable symbol strings, with a reported 10x CI speedup (explicitly not all due to the format), indexes about 4x smaller compressed, and a snapshot-testing utility reused across indexers [C10]. All figures are the vendor's. Meta's Glean takes a central, ahead-of-time approach with per-language schemas and a Datalog-like query language, on the argument that IDE-time indexing is impractical for the largest codebases [C9].

*Stack graphs* are the notable attempt to make name binding declarative *and* file-incremental. Graph construction is a purely syntactic analysis of each file in isolation, guided by tree-sitter-graph rules written once per language over the tree-sitter CST; a stack of paused lookups handles type-directed name resolution; no build or per-project configuration is needed; and it ran in production on every Python repository on GitHub from November 2021 [E11]. The README for the implementation now says that it "is no longer supported or updated by GitHub" [E12]. I could not determine why, and I will not guess; I note only that the strongest production deployment of declarative, grammar-attached name binding is no longer maintained by its creators, and the paper's own claim that other communities could self-serve support for their language [E11] was never, as far as I could tell from these sources, demonstrated at scale.

#### Synthesis for this family

Four conclusions follow from the evidence.

1. **Everything that can be derived from a grammar alone is syntactic.** Tree, errors, outline of named nodes, folding on node kinds, indentation by node kind, highlighting by token and node kind, bracket matching, and candidate tokens at a caret. Every system above agrees.
2. **Everything about names is a second declaration.** Xtext and Langium: scoping services. Spoofax: NaBL2 or Statix. Tree-sitter: locals and tags queries. Stack graphs: rule files. Marr et al.: a hook interface. antlr4-c3: a symbol table. The *expression* differs (code override, constraint language, query, graph DSL) but the existence of a second declaration does not [E1, E5, E9, E10, E13, E11, E17, E15].
3. **Defaults for names are heuristic and work for simple languages.** Langium's default (name property, container nesting, shadowing, a global export index) is explicitly a starting point [E1, E5]; Marr et al. accept name-equality candidates [E17]; tree-sitter tags are "search-based" [E13].
4. **Scale, error tolerance, and cancellation are where generated services strain.** Whole-document non-cancellable parse and CST cost [E4]; parsers that abort at the first error [E17]; error-recovery shortcomings patched by hand in gopls [C3]. The generated-service model rarely addresses these in its documentation; maintainers who have scaled it describe replacing the generated machinery [E4].

## 4. The hard problems, and the best available treatment of each

### 4.1 Error-tolerant and resilient parsing

Every serious source treats this as the first requirement. Rust-analyzer's invariant is "parsing never fails": the parser returns a tree and a list of errors, and the tree is by design incomplete, so an accessor that the grammar says is mandatory may still be absent at runtime [R6]. Matklad's tutorial gives the clearest statement of the goal: recognise as much structure as feasible, localise damage so a mistake in one function does not disturb unrelated ones, and recognise valid *prefixes* of constructs, as in an unclosed parameter list followed by a well-formed function [M4]. He contrasts that goal with the classical *error recovery* view of guessing a minimal edit that makes the input valid, and argues that for a server, clear syntax-error messages matter less than keeping the tree useful, because the editor shows the error where you type [M4]. Practical points from the same source: use a homogeneous, loosely typed concrete syntax tree so errors and trivia can appear anywhere (the approach of IntelliJ and rust-analyzer), against the fixed-shape alternative that adds placeholders between every pair of fields (SwiftSyntax) [M4]; every parse loop must consume at least one token or it will spin, which is why a later post advocates asserting that the parser advanced [M5].

**PEG-specific literature.** The central paper is Medeiros and Mascarenhas (SAC 2018). A PEG is a recursive-descent parser with ordered choice and local backtracking, so a failure is not necessarily an error: it may just mean "try the next alternative". Classical top-down error handling assumes no backtracking and so does not carry over; existing PEG tools report errors by tracking the farthest failure position or by *labeled failures*, but assume the parse then aborts [P1]. Their extension attaches a *recovery expression* to each label: when the label is thrown the parser reports the error, uses the expression to skip to a synchronisation point, and resumes. They give an operational semantics, and evaluate a Lua parser (LPegLabel) on 180 invalid programs they wrote, grading the recovered tree against the tree of the intended correct program: excellent for 56%, at least good for 91% [P1]. They compare error counts with an ANTLR-generated Lua parser (no AST available there, so only error counts): the two reported the same number of errors for about 61% of programs and ANTLR reported more otherwise, which they attribute to spurious errors [P1]. They are careful about weaknesses: a custom skip rule can swallow a large region and produce a poor tree [P1]. Concerns for a reviewer: the test set was authored by the same people as the recovery expressions, the Pascal set from earlier work was not public, and only Lua was evaluated.

The follow-up automates the annotation. Two approaches insert labels and generate recovery expressions; the *Standard* one needs manual removal of wrongly inserted labels and then gave acceptable recovery for at least 70% of files per language, while the *Unique* one is conservative, needs no manual work, and achieved 41% to 76% across Titan, C, Pascal, and Java [P2]. I read the abstract and skimmed the body. The honest reading is that **automatic derivation of recovery from a PEG gets you roughly half to three quarters of the way, and the rest is hand work**, with the evaluation again reporting the authors' own acceptance rates.

I could not obtain the work on *incremental* packrat parsing (Dubroy and Warth, SLE 2017): the only PDF copy my search surfaced was on a parser-library vendor's site, which I deliberately did not open. I know it only from a search-result abstract, which says memoisation can be made incremental and that an incremental packrat parser for JavaScript can outperform a hand-optimised non-incremental one [P3]. Treat that as unverified here.

**Other recovery designs.** Tree-sitter runs a GLR search; Lezer explores several recovery tricks in parallel and chooses by how well the parse goes a few tokens later, marking error nodes [E14]. Chevrotain, per its tutorial and issue discussions seen only in snippets, follows ANTLR3-style single-token insertion, deletion, and resynchronisation, with reports that recovery is confined to the current grammar rule and can stall inside alternatives in repetitions [E16, unverified]. Gopls patches the Go parser's recovery after the fact by "tree repair" [C3]. Marr et al. simply assume parsers abort on the first error and compensate by keeping the last good structure [E17]. The resulting design dimension is **where tolerance lives: in the parser, in a repair pass, or in the consumer**.

### 4.2 Incrementality and invalidation

The literature agrees on the vocabulary and disagrees on how much machinery is worth it.

- *Laziness over incrementality.* Matklad's thesis from 2020: neither the stub-and-index architecture nor the header-snapshot one is incremental in an interesting way; they clear caches and recompute; what makes them fast is skipping huge swaths of code [R1]. Rust forced a general incremental framework because even a crate is too big a unit of laziness [R1].
- *Query engines.* Dependency tracking with early cutoff and durability [R2], grounded in the build-systems framework [C8]. The costs are complexity, slower base-case performance, and, in his words, profiling "a special genre of hurdle racing" [R1, M3].
- *Language-dependent limits.* The update cannot be cheaper than the change in the answer [M3]. Whether a body edit can ripple into other functions' errors is a language property: in Rust, trait impls create dependencies on the non-existence of conflicting impls in every file [M3].
- *Partial incrementality with measurement.* Sorbet's fall-back-and-measure approach is the most practical report: enumerate the kinds of edit, log the reason for each slow-path fallback, and tackle the biggest reason; incremental mode was under-tested until it got 8% of the suite [C6]. A stateful incremental server accumulates errors: "even a minor bug ... will compound as more edits arrive" [C6].
- *Document-level invalidation.* Langium invalidates a whole document on change and re-links dependants through its reference index [E1]; the maintainers report that this plus a non-cancellable parse is where large files hurt [E4].
- *Persisted indexes.* gopls and clangd store derived indexes on disk for fast restart [C3, C2]; Glancer persists its whole state [G1]; stack graphs make each file's contribution independently cacheable by content [E11].
- *In-place diff updates.* For a global declaration map, update by diffing a file's old and new contribution; this beats rebuilding a persistent map, and is simpler than a query graph [M3, R1].

The lesson I draw: an author-facing design that wants incremental behaviour must say *what the unit of invalidation is* (file, declaration, query) and *what stops propagation* (a summary that did not change). Sources that cannot answer this (for example Marr et al., who reparse the whole file) are honest about it [E17].

### 4.3 Name resolution theory

Four traditions appear in the sources.

1. **Scope graphs.** Language-independent graph from language-specific rules; resolution as path finding under a calculus; proven algorithm; rename and alpha-equivalence derived [E9]. Statix generalises with constraints so types can be scopes [E10]. These are the strongest *theoretical* basis for deriving name-dependent features from a declarative description.
2. **Stack graphs.** A file-incremental, purely syntactic variant that keeps a stack of paused lookups for member access, avoiding both a build and a type checker; the authors criticise LSP servers and LSIF indexers for needing a build or configuration and for not being incremental [E11].
3. **Attribute grammars.** I read only a set of workshop slides by Hedin (2012; text extraction was partly garbled), which place JastAdd in the lineage of attribute grammars, higher-order attributes, and reference attributes. A search-result summary of the slides and of a related paper says that in reference attribute grammars a *use* node gets a declaration attribute pointing at its declaration through inherited lookup. The slides do contain an item titled "IDE name completion" in the context of a Modelica compiler, but I could not recover its content from the garbled extraction, so I treat the details as unverified. I did not read Kastens-style ordered attribute grammar papers or any JastAdd IDE-integration paper. Attribute grammars are the oldest model that resembles "semantic actions over a grammar", and the survey does not cover them adequately.
4. **Datalog-style.** I could not fetch the datalog type-checking article the rust-analyzer post cites, and I did not read primary Datalog-based name-resolution papers. The only Datalog-like system I read about is Glean's Angle, which is for indexing facts rather than editing [C9]. Treat this tradition as unsurveyed.

**Practical defaults.** Langium and Xtext default to a name property, container nesting with shadowing, and a global export index [E1, E5]. Rust-analyzer's definition maps need fixed-point iteration intertwined with macro expansion [R1, G1]. Zig's design avoids the problem by requiring explicit declarations and forbidding `use *`, so per-file name resolution is possible [M3]. The HN comment about glob imports makes the same point from the other direction [D3].

### 4.4 Macros and generated code

Macros break the per-file assumption that cheap architectures rely on. In Rust, expanding macros needs crate-wide name resolution, so "typing something in a.rs can change parsing results for b.rs" [M3]. Rust-analyzer runs procedural macros in a separate process because they may panic, crash, or be non-deterministic, which conflicts with salsa [R6]. Glancer treats macro resolution as a sub-phase of definition-map building [G1]. Matklad recommends the Sorbet-style alternative of not running metaprogramming at all and describing its effect with a shim [G2]. The rust-analyzer "heart" post makes a subtle point directly relevant to grammar-driven systems: if a macro generates types from a grammar file, find-usages inside the grammar file cannot work lazily, because the server does not know up front that the macro call must be expanded [R3]. JetBrains handles embedded languages by injecting fragments as separate files [J4]; Lezer mounts sub-trees [E14].

### 4.5 Cancellation, latency budgets, and memory

Matklad's budget for IDE reaction is about 100 ms, with update cost ideally proportional to the size of the change [M3]. Cancellation options: run sequentially (reads block writes); make state immutable and run old and new in parallel (wasteful); cancel in-flight work on the next edit and update in place (rust-analyzer); or accept relaxed consistency [M6]. He recommends prioritising writes over reads, and considering strong consistency (every answer reflects all acknowledged edits) a good default [M6]. The LSP specification's guidance puts the burden on clients to cancel and says servers should not cancel just because a change is queued [L2]; Glancer cancels in-flight queries when state changes [G1], as does rust-analyzer [M6, R6], which is the server-side behaviour the specification discourages as a default. A JavaScript server has an extra constraint: Langium's maintainers report that parsing cannot be aborted because the server cannot receive messages during it, and that moving it to workers cost more in data transfer than it saved [E4]. Memory is the other pressure: the CST share in Langium and Xtext [E4], Glancer's eager-index-on-disk design for restart speed and low RAM [G1], and matklad's claim that tree libraries should be flat arrays for the common case [G2]. The cost of a persistent server is also visible to agents: a blog about LLM tooling warns that heavy servers can use a lot of RAM [A1].

### 4.6 Consistency under concurrent edits

The protocol offers versions on documents and ordering rules [L2] but, as noted, no causal link between a client edit and a server-initiated edit [M2]. Implementations answer with virtual file systems and snapshot discipline: source generations [G1], immutable snapshots after every edit with overlays for unsaved files [C3], an input-only ground state with transactional change application [R6]. Resolve requests are stateless: a follow-up request carries enough context to recreate the earlier state, since the server keeps none [R6]. Rust-analyzer also keeps most features available when the build is broken [R6]. Note that the hardest consistency cases are not keystrokes but external changes (a package manager writing files) that the client may not report [G1].

### 4.7 Text synchronisation and position encodings

Covered in 1.3. The extra points: line-ending detection per file is needed when producing edits [G1]; conversion between UTF-8 offsets and protocol positions should be isolated at the boundary and use cached line indexes [G1, C3]; the specification's negotiated encodings now allow a UTF-8 server to avoid conversion if the client agrees [L1].

### 4.8 Multi-file and workspace models

Three models appear. *Index plus per-file analysis* (IntelliJ stubs, Sorbet's earlier design, Xtext and Langium's global scope of exported descriptions) [R1, J4, E1, E5]. *Project/build-derived units* (clangd compile commands, gopls views and snapshots, rust-analyzer's crate graph, all taken from a build tool) [C2, C3, R6]. *Purely syntactic cross-file* (stack graphs) [E11]. The VS Code guide ships a sample that starts one server instance per workspace folder for multi-root workspaces [V2]; Glancer chooses one process per workspace and notes the protocol does not help [G1]. The Langium lifecycle shows the simplest explicit workspace model: collect all files with the language's extensions at start-up, parse them, index exported symbols, then link and validate; a change invalidates dependants via reference descriptions [E1]. A question the sources leave open is what a language does when a file's role depends on a *parent* declaration (Rust's `mod foo;`), which rust-analyzer handles by rebuilding the crate's module tree on every change [R3].

### 4.9 Type-dependent features

Completion after a dot, inlay hints, hover inside bodies, and many diagnostics need types [G1]. The parse-based approaches stop short on purpose: Marr et al. leave typed languages as future work and accept undefined variables in completion [E17]; the c3 engine leaves it to a symbol table [E15]; Langium has no default type computation [E1]. Statix's argument is that types can be expressed in the same graph as names [E10]; stack graphs handle member lookup by pausing a resolution to resolve another name, which is type-directed but not type inference [E11]. Pyright's lazy evaluator and rust-analyzer's laziness at body level show how expensive type work is kept off the critical path [C5, R6, G1].

### 4.10 Formatting

I found little deep treatment in the sources I could read. Formatting needs a lossless tree with trivia [M4, R5] and range and on-type variants exist in the protocol (3.18 adds multi-range formatting) [L2]; JetBrains' LSP client added range formatting in 2026.1 and on-type formatting, disabled by default, in 2026.1.2 [J1]; line endings matter for edits [G1]. Langium's documentation lists a formatting recipe that I did not read. Matklad has recent posts on formatter steering that I did not read. This is a gap in the survey.

## 5. Browser and embedded use

The browser changes three things: there is no process to spawn, the editor may not be VS Code, and the main thread is precious.

**Monaco.** The monaco-editor package is "artificially extracted" from VS Code, so a client written for the VS Code API does not run on it. TypeFox started monaco-languageclient in 2017 as a bridge, then had to re-implement parts of the VS Code API, and from 2022 relied on a separate project that modularises VS Code's own code into ES modules; in 2025 version 10 folded the application toolkit back into the main package [B1]. Connections can run over a WebSocket to a server elsewhere, or entirely in a browser web worker using the protocol's browser transport, which is the route TypeFox documents for running a Langium-based server in a page (search-result summary of its README) [B1]. The maintainers' history is itself evidence of how much glue the in-browser LSP route needs in practice, which is in tension with matklad's claim that glue is small [M1]; the difference is that the Monaco route is trying to reach VS Code features without VS Code.

**CodeMirror 6.** CodeMirror's own model is in-process: a language package contains a parser (usually Lezer), node-level metadata for highlighting, indentation, and folding, and optional language-specific extensions such as autocompletion [E14]. LSP is an add-on, for example a community plugin that connects an editor to a server over a WebSocket and provides completion, hover, diagnostics, definition, highlight, formatting, and rename [B2]. I read only the plugin's README.

**Servers in workers and WebAssembly.** VS Code's team recommends running WebAssembly code in a worker so as not to block the extension host, and shows creating a language server in a language that compiles to WebAssembly [V5]. TypeFox's Pyright browser package, per its README, uses a worker which starts the server and a nested worker for the analysis [B2]. A community port of clangd to the browser, per search snippets I did not open, needs cross-origin isolation for shared memory [unverified]. My reading is that a pure-JavaScript analysis engine is the least costly to deploy in a page, which the TypeFox Pyright and Langium examples suggest, but I found no source that compares deployment costs systematically.

**In-process language service versus protocol server.** The architecture documents of the best servers make the same recommendation: keep a protocol-independent core and put LSP at the edge. Rust-analyzer's `ide` crate is explicitly not shaped by LSP and could serve "custom flatbuffers-based protocol or just ... as a library in your text editor" [R6]. Matklad advises treating LSP "as a serialization format" [M1]. The TypeScript team is moving its server to LSP to align with other languages, while an API for embedders came later [C4]. For an in-browser editor, the practical consequence is that a design with a clean, serialisable service interface can be hosted as a direct call, a worker message, or a JSON-RPC server, whichever the editor wants; a design coupled to LSP types cannot. A cost of the in-process route is losing the protection that the separate process gave: VS Code's own guide gives CPU and memory isolation as a reason for separate server processes [V2], and in a browser the worker is the substitute.

## 6. Testing and validation practice

**Snapshot tests with markers.** Rust-analyzer's testing guide describes tests that are "a piece of input text ... and some output text", compared with the expect-test crate, with `$0` marking the cursor, `$0...$0` a range, and `// ^^^ label` annotating the line above [R7]. Parser tests are data-driven: a directory of source files each with a stored expected tree, regenerated with an environment variable [R6]. The guide is candid about an oracle problem: type mismatches in tests "are determined via rust-analyzer's own analysis, not the compiler", so tests can pass despite missed or bogus mismatches [R7]. Matklad's view of the practice is "if I need to test something, I write a property/fuzz/randomized test; if I can't fuzz, I write a snapshot test", with an update mode that rewrites the expected literal [M9]. His minimal property-testing library draws all randomness from a finite pre-generated byte string so a failing case can be shrunk by shortening the input [M10]. I only skimmed those two posts.

**Fuzzing.** LspFuzz (ASE 2025) claims to be the first fuzzer for LSP servers: it mutates source code in a syntax-aware way and dispatches editor operations in context, uses grey-box coverage, and in tests on four widely used servers found crashes; 51 bugs were reported, 42 confirmed, 26 fixed, and two received CVE numbers [T1]. The paper notes about 300 server implementations and 50 editors, and that clangd alone has over 500 crash issues [T1]. The oracle is a crash, so it says nothing about wrong answers.

**Differential testing and comparing with the compiler.** I found no paper on differential testing of a server's semantic answers against the language's compiler. The practical examples are internal: Sorbet's tests of incremental mode, which implicitly compare against the full check [C6]; and the Marr et al. comparison of parse-based features with an execution-based baseline, which is qualitative [E17]. The PEG recovery papers compare the recovered tree with the tree of the intended correct program [P1], which is a reasonable oracle for *syntactic* recovery but only as good as the test set. SCIP's authors built a snapshot-testing utility on top of their format and say it made indexers easier to test than LSIF payloads [C10].

**Metrics that matter to users.** The sources' latency numbers are: a 100 ms budget for reaction to an edit [M3]; project-load time 9.6 s versus 1.2 s for TypeScript on VS Code's code base [C4]; the fraction of edits that take a slow path (19% to 10%) in Sorbet [C6]; a 215 ms parse of 10,000 lines [E17]; and 1000+ ms responses for files above 1 MB in Langium [E4]. Time to first diagnostics and keystroke latency are the metrics users feel, yet apart from the Sorbet fallback rate, the TypeScript project-load time, and the Langium degradation report, I found few published measurements in that form, and none of the three is reproducible from the text alone. I did not read matklad's 2026 post titled "Benchmark In Milliseconds" and it may be relevant.

**What the LSP conformance picture looks like.** I did not find a conformance test suite for servers; the protocol's meta model supports code generation of types [L2, C3], which constrains syntax, not behaviour. This is a negative finding from limited searching.

## 7. Current debates and recent developments, 2023 to 2026

**Is LSP the right abstraction?** The strongest critiques come from people who built servers. Matklad (2023): RPC where state synchronisation is needed, UTF-16, lost causality, no multi-step refactors [M2]. The Go team (2025 to 2026): interactive refactorings cannot be expressed [T2]. The rust-analyzer project's own list of non-standard LSP extensions is a standing record of what the protocol cannot express [R8]. Hacker News commenters add: configuration has no blessed mechanism; a protocol over a socket where in-process calls would do; the "projection" model in which the server owns the code and the files are an output [D1]; and a recurring claim that LSP plugins are broken or that Microsoft controls the ecosystem, which I report as opinion [D1, D2]. The defenders' position is not that LSP is elegant but that it fixed the equilibrium [M1]. VS Code's own pages treat the protocol as plainly beneficial [V1, V2].

**LSP versus native IDE APIs.** JetBrains' documentation says LSP is not a replacement for its Language API [J1]; the same company is open-sourcing its client and accepts that niche language communities, which cannot afford a full platform plugin, want LSP [J2, J3]. In 2026 its client still lacked rename until 2026.1.1 [J1]. This is the clearest picture I found of the trade-off: the protocol gives reach, the native API gives depth.

**Tree-sitter-based tooling.** Tree-sitter supports highlighting, locals, and tags queries and provides search-based navigation [E13]; matklad says to "just use Tree-sitter" for a quick result and sees it as the basis for features like fold-bodies-by-default in editors that do not use a server [M4, M8]. GitHub built precise navigation on top of it and then stopped maintaining that work [E11, E12]. The tension: syntactic tooling is cheap and robust, and semantic precision costs a second declaration.

**Query-based or not.** Matklad's 2026 turn is the main event [M3]. Glancer's persisted-eager design is an alternative with its own trade-offs (more initial time and RAM, near-instant restart) [G1]. Sorbet's experience says the simple approach works until base speed degrades [C6]. TypeScript chose a native rewrite over adding query machinery [C4]. Matklad also calls rowan, the tree library behind rust-analyzer, "garbage" for the common case of shallow analysis of dependencies, though he concedes it suits incremental parsing and tree-mutating refactors [G2].

**Server-side versus client-side features.** The recurring example is folding and outline: derived from syntax, and in matklad's view better "lowered to plain text" in the editor than implemented as dedicated GUI [M8]; but LSP currently lacks the kind needed [M8]. LSP 3.18's refresh request for folding ranges shows folding is being treated as server-derived state [L2].

**Language servers as infrastructure for coding agents.** By 2026 blogs and READMEs describe coding agents using language servers for go to definition, find references, call hierarchy, and diagnostics after edits, with the argument that semantic lookup beats text search and the caveat that heavy servers consume RAM [A1]. One blog claims that text-search-based agents typically find only a fraction of a function's usages [A1]; that is an uncontrolled claim. A toolkit, Serena, packages symbol-level retrieval and editing over language servers for agents through MCP [A1, README]. A commenter on the Glancer thread reports switching to ctags after reading posts that "grep is better than LSPs for LLMs" [D3]. I found nothing here beyond blog-level evidence. The relevance to this survey is that agents want complete, deterministic answers on code that compiles, which is the *second* of the two jobs the same commenter distinguished: best-effort editing help versus exhaustive analysis [D3].

**Dissenting and critical voices I cannot weigh.** A commenter quoting a 2019 talk by Jonathan Blow calls LSP "a more complicated, slower way to do libraries" [D1; I did not watch the talk]; that is reported second-hand and I do not rely on it.

**Where sources disagree, and who I find more credible.**

- *Is M x N the reason LSP exists?* Microsoft's documentation says yes [V2]; matklad says no [M1]. I find matklad more credible on the evidence he gives (small glue code, multiple clients per editor, a spec that was informal), though his figures are unverified by me and the critics' point that the diagram is a stylised argument stands [D2].
- *Should servers cancel on new edits?* The spec advises against server-initiated cancellation merely because a change is queued [L2]; rust-analyzer does cancel [M6]. These are two valid points on the consistency/latency trade-off. The spec is describing a protocol-level courtesy; the implementation is making a memory-model choice.
- *Span-based or syntax-based lookup?* Rust-analyzer says spans are too slow and lose syntax identity [R3]; Glancer says span-based works with full analysis resident [G1]. Both are consistent with their architectures; neither measured the alternative.
- *Is a generator for servers feasible?* Rascal's documentation claims near-zero cost [E6]; Neverlang's authors say Xtext alone generates servers [E18]; Spoofax 3's status page does not list server generation [E7]; Marr et al. get under 1,000 lines per language only for dynamic languages and at reduced precision [E17]. I find Marr et al. most credible because they state their limits, and I treat the other claims as marketing or self-reports until shown.

## 8. What this means for anyone proposing to derive a language service from a grammar

The literature does not say it cannot be done. It says that the part that can be derived is smaller than people hope, that the part that cannot be derived must be given a *declared home*, and that the places where such designs fail are well documented. A proposal in this space should be able to answer the following questions, each of which has a source behind it.

**What is derived, what is declared, what is code?**
1. Which features come from the grammar alone (tree, errors, outline, folding, syntactic completion) and which need a second declaration (names, scopes, types)? [E1, E5, E13, E15, E17] Systems that are candid state the split in a table; systems that are not use words like "almost zero cost" [E6].
2. How is the second declaration expressed (code override, constraint language, query, graph rules), and what would an author's existing code have to change to supply it? [E1, E10, E13, E11]
3. What does the default name resolution do when the author declares nothing, and where is it wrong? Name equality, container nesting with shadowing, and search-based navigation are known defaults with known failure modes [E1, E17, E13, D3].
4. For each feature, what is the result when the tree is incomplete? Is there a listed behaviour for completion at a cursor inside an unfinished construct [G1, M4]?

**Incomplete and erroneous input**
5. How does the parser behave on the first error: abort, recover, or repair afterwards? [P1, P2, E17, C3] If recovery is added, who writes the recovery expressions, and how was their quality measured against something other than the authors' own test cases? [P1, P2]
6. Can a loop in author-supplied code spin when a rule consumes nothing? [M5]
7. Does every feature degrade gracefully, or does one syntax error blank outline, folding, and highlighting? [R6, M4]

**Incrementality, latency, and cancellation**
8. What is the unit of invalidation, what stops propagation, and what fraction of realistic edits fall to a slow path? Is the slow-path reason measured? [R2, C6, M3]
9. Is the parse cancellable and is it kept off the thread that receives edits? [E4, M6, G1]
10. What are the latencies on files of different sizes, measured how, on whose hardware? [M3, E4, E17]

**Names, symbols, and cross-file behaviour**
11. What is the symbol model: how are definitions identified across files, what happens with duplicate or missing definitions, and is rename derived from the same structure as resolution, as in scope-graph theory? [E9, E1]
12. What is the workspace model: how are files discovered, how does a changed file invalidate dependants, how are multiple projects handled? [E1, G1, C3]
13. What does the design say about macros, generated code, and embedded languages? [R3, G2, J4, E14]

**Protocol and hosting**
14. Is there a protocol-independent service interface, and are LSP, worker, and in-process hosts all thin adapters over it? [R6, M1, B1]
15. How are position encodings, line endings, and document versions handled at the boundary? [L1, G1, M2]
16. Which features does LSP fail to express for this language (for example a function-body folding kind), and what does the design do about it? [M8, R8, T2]

**Evidence and adoption**
17. Against what independent oracle was each feature tested? A reference compiler, a second implementation, or only the tool's own output? [R7, P1, E17]
18. Are the test inputs the authors' own? How many languages, how large, and were failures reported? [P1, E17, E18]
19. What is the migration path for an author who already has semantic actions or a language server? The one precedent I found migrates the grammar but not the semantic code [E3], and the generated-grammar ecosystems report that the semantics are where the effort is [E1].
20. What happens in five years? Stack graphs were the most ambitious deployment of declarative binding and are no longer maintained by their creator [E12]; Spoofax 3 is incomplete [E7]; LSIF was replaced by SCIP within a few years [C10]. A design should say who maintains the pieces that cannot be generated.

## Limits of this survey

- **Depth.** About 50 sources were read in full, most, or in the relevant sections; about 20 more were only skimmed or had only their contents read (the bibliography marks each). Papers on scope graphs, Statix, and attribute grammars were read at abstract-and-introduction depth, so my statements about them are statements about their claims, not checks of their proofs.
- **Not covered or only thinly covered:** Datalog-based analysis for IDEs; Kastens-style attribute grammar systems and Silver; incremental parsing literature (Wagner and Graham, incremental packrat parsing: not obtainable); Roslyn's own documentation beyond Lippert's tree post; the Kotlin Analysis API; JetBrains Fleet; formatting; notebooks; conformance suites; the Dart analysis protocol and the Rider protocol (known only through matklad's description).
- **Vendor and self-reported numbers** (TypeScript speedups, Pyright speed, Sorbet percentages, TypeFox percentages, SCIP sizes, Typelang character counts) are repeated here as claims, not facts.
- **Discussion threads** are cited as discussion; I could not verify their counts beyond what the search API returned.
- **Dates.** The LSP 3.18 date is read from a changelog whose date format is not declared; the TypeScript 7 release is known only from search snippets.
